# 48Date web — project rules

4. Match size, weight, line-height, colour, spacing and radius exactly. Never substitute "the nearest class"; add a token instead (rule 8).

## Structure
5. TypeScript only. Server Components by default; `"use client"` only on interactive leaves (accordion, reveal observer, section scroller, phone/OTP steps).
6. One piece per file, kebab-case file names, named exports.
7. Folders (all under `src/`):
   - `app/` — routes, layouts, metadata only. No markup beyond composing sections.
   - `components/ui/` — shadcn primitives (rule 23).
   - `components/pieces/<type>/` — reusable, page-agnostic pieces, one folder per kind: `actions`, `brand`, `cards`, `content` (text, icons, chips), `feedback` (status, progress), `forms`, `illustrations` (non-interactive landing art), `layout`, `media`, `overlays`, `shells` (page frames, headers, guards). A new piece goes in the folder of its kind (see Pieces registry).
   - `components/sections/<page>/` — one file per Figma section, composed from pieces. The portal is split by feature: `sections/portal/<shared|discover|matches|chats|dates|games|stories|profile|settings|membership>/`.
   - `hooks/` — every React hook that isn't tied to one component (`use-loaded`, `use-now`, `use-match-clock`, `use-date-plan`, `use-member`, `use-member-location`, `use-onboarding-options`, `use-plans`, `use-service-action`, `use-session`). Store modules that export a hook (`lib/onboarding/profile-draft.ts`) keep it beside their store.
   - `data/` — all copy, image paths, alt text, icon names and actions, typed.
   - `stores/` — the only way components read `data/`.
   - `lib/` — helpers, the scale files (rule 8) and one folder per feature service (`lib/auth`, `lib/onboarding`, `lib/portal`); each service's marked mock lives in that feature's `mocks/` folder and its API implementation beside the contract (`api-*-service.ts`).
   - `lib/api/` — the HTTP layer only (rule 41): `config.ts`, `endpoints.ts`, `client.ts` (REST, uploads, SSE `stream`), `socket.ts` (Socket.IO), `query-client.ts` + `cache.ts` (TanStack Query), `tokens.ts`, `errors.ts`, `types/<module>.ts` and `modules/<module>-api.ts` (with `modules/cache-keys.ts`). Screen query keys live in `lib/screen-keys.ts`.
8. Scale files: every design token lives in `src/app/globals.css` (`@theme` / `@utility`) **and** is registered in a `lib/` scale file — type classes in `lib/type-scale.ts`, control sizes in `lib/control-sizes.ts`, surfaces/tones in `lib/tones.ts`. Components reference the scale map, never a raw token class string.
9. No raw hex, px literals or copy inside components. Arbitrary Tailwind values are allowed only for one-off geometry taken from Figma (collage offsets, image aspect ratios).

## Content, links, assets
10. Components read content through `src/stores/*` (e.g. `getLanding()`), never by importing `src/data` directly.
11. Every link targets a screen code through `hrefFor(screen, section?)` in `lib/routes.ts`. No literal hrefs in components or data.
12. Actions without a known destination use `notFunctional(reason)`; they render as `aria-disabled` buttons carrying the reason, so they're easy to find and wire later.
13. Icons are Hugeicons, named in data by their Hugeicons slug and rendered by the `Icon` piece from `public/icons/<slug>.svg` (exported from Figma — Hugeicons Pro, Solid Rounded — normalised to a full-box viewBox, coloured with `currentColor` via CSS mask).
14. Images use `next/image` with an accurate `sizes`; `preload` (Next 16's replacement for the deprecated `priority`) only on the hero image.
15. Download each asset once into `public/`, comparing bytes against existing files before adding.

## Pieces
16. Every piece accepts `revealDelay` (ms) and reveals through the `Reveal` piece. Atoms that only ever render inside another piece (`Icon`, `Chip`, `IconBadge`, `RichText`, `ActionTarget`, `Container`) are exempt — their parent reveals them.
17. Visual differences are props (`size`, `variant`, `tone`). Call sites may pass `className` only for placement (grid/flex position, margins), never for colour or type.
18. Merge classes with `cn()` from `lib/cn.ts`.
19. No duplicated markup, class strings or literals: a pattern used twice becomes a piece or a shared constant.

## Quality
20. Accessibility: landmarks (`header`, `nav`, `main`, `footer`), exactly one `h1` per page, alt text from data, `aria-label` on icon-only controls, visible focus ring (`focus-ring` utility), full keyboard navigation.
21. Motion respects `prefers-reduced-motion` (reveal and accordion animations switch off).
22. Fonts load only through `next/font` (Manrope).
23. shadcn primitives in `components/ui/` are cleaned up: drop unused exports/variants, replace default palette classes with project tokens, remove `dark:` styles the design doesn't have, keep `data-slot` attributes.
24. Landing display type (≥28px) is fluid: it reaches the exact Figma size at the 1920px frame width and scales down to a set minimum at 390px (formula in `globals.css`), so narrower desktops keep the Figma composition instead of re-wrapping headlines. Text ≤24px is fixed. Authentication type (`type-auth-*`) is fixed: its frames are drawn at 1440 and the responsive specimens keep the same sizes.
25. Keep the Pieces registry below current: add every new reusable piece with path and props.
26. `npm run lint`, `npm test` (Vitest: unit tests beside the code, and `src/test/api-contract.test.ts`, which runs the real API services against the Postman collection's example responses through `src/test/postman-replay.ts`) and `npm run build` must pass with no new warnings before work is called done. A service change that touches an endpoint gets a contract test.
27. Never commit or push unless asked.
28. Legal pages use the draft structure from Figma; their copy is not approved for release.
29. Record design-silent decisions under "Decisions" below.
30. New lasting rules are appended here; `CLAUDE.md` only points to this file.
31. Routing is path-based, never `#hash`. A section is a URL segment (`/how-it-works`, `/terms/community-conduct`) served by an optional catch-all route (`[[...section]]` / `[[...step]]`) that prerenders every value with `generateStaticParams`, resolves `params` inside `<Suspense>` (the page itself is the instant fallback) and brings the section into view with `ScrollToSection`. `hrefFor(screen, section)` builds these paths; section links use `scroll={false}`.
32. Interaction states of one Figma flow step (PHONE-ERROR, OTP-FILLED, OTP-ERROR, OTP-RESEND, OTP-EXPIRED, OTP-LIMIT, VERIFY-PROCESS…) are client states on that step's URL, not separate routes. Each URL is keyed in `lib/routes.ts` by the screen code that opens it.
33. Authentication screens talk only to `authService` (`lib/auth/auth-service.ts`). It currently points at a clearly marked mock; swap the implementation there, never inside components. The entered phone number lives in `sessionStorage` between steps, never in the URL.
34. Onboarding screens talk only to `onboardingService` (`lib/onboarding/onboarding-service.ts`, currently a clearly marked mock) for nickname checks, area search, uploads and selfie review. Answers live in the `profileDraft` sessionStorage store (`lib/onboarding/profile-draft.ts`) and are saved as they change, so Back never discards them; photos stay in memory as object URLs (`lib/onboarding/photo-store.ts`) and every URL is revoked when discarded. Storage values are validated on read; nothing is sent anywhere until a real API exists.
35. Every onboarding step is `SetupShell` (route level) + one `SetupStep` (heading, content, Back / primary row). Step order, numbers and Back / Continue targets come from `data/onboarding/flow.ts`; never hard-code the next step in a component. Browser permissions (location, notifications) are requested only from a click, and only an approximate area label is kept, never coordinates.
36. The verification camera is opened only from "Allow camera & continue", its tracks are stopped whenever the capture screen is left or the page unmounts, and the selfie lives only as an in-memory object URL that is revoked once it is submitted or retaken. The review result comes from `onboardingService.getVerification()`; the badge is shown only once it is `verified`.
37. Member portal screens talk only to `portalService` (`lib/portal/portal-service.ts`, currently a clearly marked mock) for preferences, the discovery deck, decisions and matches. Match deadlines are server-owned: components count down to the service's `expiresAt` and never invent one. Every portal page is `PortalShell` (route level) + a view from `sections/portal/shared/portal-page.tsx`; member pages link with `toItem(screen, memberId)` (a path segment that opens at the top, unlike a `section`). Live countdown text is never a live region (`StatusBadge live={false}`, the `deadline` note). Date planning talks only to `dateService` (`lib/portal/date-service.ts`, a marked mock); the chosen venue, date and time live in the plan, never in the URL. Actions whose page belongs to the member on screen are `MemberLink`s in data, resolved with `forMember()`. Games talk only to `gameService` and stories only to `storyService` (both marked mocks in `lib/portal/`); a story is published only after moderation and a failed submission keeps its draft. Messaging talks only to `chatService` (`lib/portal/chat-service.ts`, also a marked mock); photos and voice recordings stay in memory as object URLs, the microphone opens only from "Start recording" and is released when the screen is left (as rule 36).
38. Route guards are client-side `SessionGate`s backed by `authService.hasSession()`: portal and onboarding content is members-only (signed-out visitors go to SIGNIN), the sign-in / sign-up entry forwards members to DISCOVER. SESSION and AGE-GATE "Leave sign up" call `authService.signOut()`, which clears every `48date.*` key and the in-memory photos. The API base URL comes only from `NEXT_PUBLIC_API_BASE_URL` (`lib/api-config.ts`, `.env.example`); no secrets in code.
39. Profile, trust, settings, notification choices, reports and deletion talk only to `accountService` (`lib/portal/account-service.ts`, a marked mock); blocking and unblocking stay in `chatService` and the verification status comes from `onboardingService.getVerification()`. The forms check `lib/portal/account-rules.ts` first and also show the field errors the service returns, keeping every value. Private account details never appear on the public profile. Account deletion needs the confirmation box and then signs the member out. Every portal view is wrapped in `PortalGuard`: OFFLINE when a view is opened without a connection, GLOBAL-ERROR (`catchError` from `next/error`) when it throws.
40. Membership, checkout, restore, renewal and the free conversation quota talk only to `membershipService` (`lib/portal/membership-service.ts`, a marked mock). Entitlements come only from the provider's confirmed result, never from a click: PAY-PROCESS waits for `checkout()`, and MEMBERSHIP reads `getMembership()`. Payment happens on the provider's hosted page; the app never renders card fields or stores card data. Subscription terms must be agreed before payment.
41. API integration (Postman `postman/48Date-Backend.postman_collection.json` and `48Date-WebSockets.postman_collection.json` are the contract; the Admin folder is not called from this app). Each service contract picks its implementation once: `apiEnabled ? api…Service : mock…Service` (`NEXT_PUBLIC_API_BASE_URL` set or not), so the app runs without a backend. Components never call `fetch`, `lib/api` or a path: they call the service, the service calls `lib/api/modules/*`, and those call `api` from `lib/api/client.ts` with paths from `lib/api/endpoints.ts`. Request and response shapes live in `lib/api/types/<module>.ts` and match the collection field for field (case-sensitive enums). The client adds the bearer token, refreshes once on 401 with a single shared refresh (the API rotates refresh tokens and revokes reused ones), normalises both failure envelopes into `ApiError` and supports `AbortSignal`. Tokens live only in `lib/api/tokens.ts`: the 15-minute access token in memory, the rotating refresh token in localStorage shared by every tab, and every refresh runs under a browser-wide Web Lock that re-reads the newest token (a reused refresh token makes the API revoke the whole session). Only a 401 / 403 from the refresh signs out; a 429 / 5xx keeps the session. Signing out in one tab signs out all tabs. Every connected view has loading, empty and error states (`sections/portal/shared/load-failed.tsx`; `failureReason()` shows the API's own 4xx message).
42. TanStack Query is the only client cache (`lib/api/query-client.ts`: one browser client shared by React and the API modules, a new one per server render so member data is never shared; `QueryProvider` in the root layout). Screens read services with `useLoaded(screenKeys.x, service.fn)` — never `useEffect` + `useState` for server data — and apply results with `queryClient.setQueryData` where a service returns the new state. API modules wrap shared GETs in `cached(key, staleMs, load)` (dedupes concurrent calls, reuses the value); writes `invalidate` the keys they change; screen keys nest under the module keys (`lib/screen-keys.ts`) so one invalidation refreshes both. Sign-out and a rejected refresh call `clearCache()`, which also resets session state registered with `onCacheClear` (decks, chat rooms, the socket).
43. Live data comes from the server, not from polling: run progress (discovery decks, auto-matching, venue suggestions, AI suggestions, selfie review) is read from the SSE endpoints through `api.stream` (bearer header; one snapshot read if a stream drops), and chat, receipts, typing, conversation closing and game answers come through `lib/api/socket.ts` (opened only while a screen needs it, token re-read on every reconnect, closed on sign-out). Where polling is unavoidable it is chained (TanStack `refetchInterval`, or `pause()` loops), slow while the socket is up, and stops when the screen closes. Fetch only where the screen shows the data and never one request per list row: lists carry their own member summaries.
44. Member pages are keyed by the member's nickname (the API's public id, also the name shown); `MemberId` is a string. Only sample members prerender; with the API any segment matching `memberIdPattern` (and story ids) renders on request, and the page shows MEMBER-UNAVAILABLE / MATCH-EXPIRED when the member or match doesn't exist. Member photos from the API render `unoptimized` (`isRawImage`), only http(s) URLs or keys under `NEXT_PUBLIC_MEDIA_BASE_URL` are used (`mediaUrl`), and the server never fetches them.

45. Request safety: every call goes through `lib/api/client.ts`, which only sends the token to the API origin (no other origin, no cookies). Rate limiting is the backend's job: the client has no limiter of its own (the backend team's decision). `api` and `endpoints` are frozen. `next.config.ts` sends the security headers (CSP without nonces — they don't work with partial prerendering — limited to the API, its socket and Google sign-in; nosniff, `DENY` framing, referrer and permissions policies). With the API on, screens show only service data: sample copy is for the mocks (`liveData` in `lib/portal/live.ts`), and loading shows nothing rather than a sample. The server is the authority for limits and permissions.
